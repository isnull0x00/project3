# 예측 방법을 고른 과정

노선별 일별 이용자 수 예측과 시간대별 예측을 어떻게 만들었는지 정리한 문서입니다.
README의 "예측 서버와 시간대별 예측"에 나온 수치의 근거와 조건을 모았습니다.

## 한눈에 보기

| 단계 | 결론 | 핵심 숫자 |
|---|---|---|
| 정답 데이터 | 울산 승하차 API가 폐기되어 국토교통부 노선별 이용량 API로 바꿈 | 울산 5개 구 738일 수집, 노선 개편(2024-12-21) 이후 601일 · 194개 노선으로 학습 |
| 변수 | 크게 반응한 것은 달력뿐 | 평일 공휴일 평소의 0.52배, 설·추석 당일 0.21~0.24배, 큰 비 약 −9% |
| 후보 비교 | 단순한 규칙이 기계학습 6개보다 낮은 오차 | "같은 유형 날 평균 × 휴가 보정" 최종 10.9% |
| 일별 예측 | 평균 약 11% 어긋남 | 하루 1,000명이 타는 노선이면 평균 약 109명 차이 |
| 시간대별 예측 | 일별 예측 × 시각 비율 | 비율 오차 13.9%, 일별 오차까지 합친 평일 16.2% |

오차율은 (예측과 정답의 차이 합) ÷ (정답 합계)이고 낮을수록 좋습니다.

## 1. 정답 데이터

울산 승하차 API는 인증 오류 뒤 담당 부서 문의에서 폐기 회신을 받았습니다. 후보 4개를 비교해
국토교통부 노선별 이용량 API로 바꿨습니다.

- 위치 파일은 승하차 인원이 없었고, 정류장별 파일은 날짜별 변화를 볼 수 없었으며, 교통카드 빅데이터는 손으로 내려받아야 해서 제외했습니다.
- 이 이용량은 AI 합성데이터라서, 아래 오차는 실제 승객 수가 아니라 이 정답값 기준입니다.

## 2. 변수

기상, 방문자 수, 행사를 시험했지만 크게 반응한 것은 달력(요일·공휴일·명절)뿐이었습니다.
큰 비는 약 −9%였고 기온과 바람은 변화가 없었습니다. 방문자 수는 한 달 늦게 공개되어
예측에 쓸 수 없었습니다.

## 3. 후보 9개를 같은 조건으로 비교

- 규칙 3개: 같은 요일 평균, 같은 유형 날 평균, 같은 유형 날 평균 × 휴가 보정
- 기계학습 6개: Ridge, 랜덤 포레스트, 엑스트라 트리, HistGradientBoosting, XGBoost, LightGBM
- 예측하는 날의 실제 값은 숨기고 그 전 자료만 주어 맞히게 했습니다.

| 모델 | 고르는 시험(여름 6주) | 최종 확인(마지막 56일) |
|---|---|---|
| **같은 유형 평균 × 휴가 보정** | **8.1** | **10.9** |
| 같은 유형 평균 | 9.3 | 11.7 |
| 같은 요일 평균 | 11.3 | 16.7 |
| 엑스트라 트리 | 11.5 | 11.9 |
| 랜덤 포레스트 | 11.6 | 11.8 |
| HistGradientBoosting | 11.6 | 12.2 |
| XGBoost | 11.8 | 12.0 |
| LightGBM | 11.9 | 12.2 |
| Ridge | 12.6 | 11.3 |

- Ridge는 두 시험의 순위가 뒤바뀌어(12.6 → 11.3), 한 번의 시험으로 순위를 정하지 않았습니다.
- 기계학습 5개는 서로 1%p 안에서 비슷했고, 규칙 사이의 차이(8.1 ↔ 11.3)가 더 컸습니다.
- 겨울 12주를 따로 채점해도 휴가 보정 규칙이 8.7%로 순서가 같았습니다.
- 기계학습이 이기지 못한 이유는 입력 힌트가 달력 구조뿐이고 "최근 이용량"이 들어 있지 않기 때문으로 추정합니다.

## 4. 시험을 둘로 나누기

방법을 고르는 시험(여름 6주)과, 고른 뒤 한 번만 보는 최종 확인(마지막 56일)을 나눴습니다.
56일은 모델이 "학습 마지막 날 + 56일"까지 예측하도록 허용하는 한도와 같게 정한 값입니다.

## 5. 오차는 어디서 났나

최종 확인 56일을 구간별로 나눠 보았습니다.

| 구간 | 일수 | 평균 어긋남 | 전체 오차 중 몫 |
|---|---|---|---|
| 08-14 ~ 08-31 휴가 직후 | 18일 | 약 8.5% | 24% |
| 09-01 ~ 09-23 평범한 가을 | 23일 | 약 11.1% | **46%** |
| 09-24 ~ 09-27 추석 | 4일 | 약 21.2% | 6.5% |
| 09-28 ~ 10-08 추석 뒤 | 11일 | 약 12.0% | 23% |

처음에는 추석이 오차의 주된 원인이라고 예상했지만, 추석은 4일뿐이라 몫이 6.5%였습니다.
가장 큰 몫은 평범한 가을 평일 23일이었습니다. 예측 평일 값은 기간 내내 거의 일정했는데
실제 평일 이용은 8월 말에서 9월 중순 사이에 올라갔습니다.

## 6. 휴가 보정과 막힌 일

**휴가 보정**: 큰 오차가 여름 휴가철 초입과 휴가 뒤 회복에서 나왔습니다. 휴가 구간을 달력으로 정해 평균에서 빼고 세는 보정을 더하자, 8월 휴가에 걸린 시험 구간의 오차가 20.7%에서 8.8%로 줄었습니다. 시험 구간을 자르는 위치에 따라 오차가 흔들려서(10.1~20.7%), 숫자를 한 점이 아니라 끝 날짜 여섯 곳의 범위(약 8.5~11%)로 말합니다.

**막힌 일 4가지**

1. **"5개 구가 모였다"는데 정답이 노선 4개 · 96행뿐**: "지나는 구의 수"와 "받은 구의 수"라는 이름이 비슷한 두 값을 헷갈려 데이터 대부분이 조용히 걸러졌습니다. 수집 기록으로 5개 구를 모두 받은 날을 판정하도록 고쳐 5,014행 · 196개 노선을 확보했습니다.
2. **가까운 날(1~14일)이 먼 날(15~28일)보다 더 틀림 (15.5% 대 7.7%)**: 평균 하나로는 보이지 않아 날짜별로 쪼개니 8월 첫 주와 추석 주가 크게 틀렸고, 그때 학습 자료에 여름휴가와 추석이 한 번도 없었습니다. 모델은 두고 수집 시작일을 앞당겨 2025년 여름을 포함했습니다.
3. **예측 범위와 시험 범위가 서로 다른 파일에 따로 적힘 (90일 대 28일)**: 검증하지 않은 거리의 숫자를 내보내지 않도록, 검증 거리 · 시험 일수 · 허용 한도를 56일 하나로 맞췄습니다.
4. **병렬 수집이 4분 만에 멈췄는데 로그는 "알 수 없는 응답 구조"**: 서비스 장애 응답이 JSON으로 왔는데 코드가 처리하지 못해 키 문제처럼 보였습니다. 장애 코드를 알아보게 해 재시도를 5번에서 2번으로 줄이고, 오류 문구에 코드를 표시했습니다.

## 7. 시간대별 예측

일별 예측(하루 합계)에 (노선, 날 유형, 시각)별 비율을 곱합니다. 예를 들어 134번 평일 하루 합계 9,713명에
16시 비율 약 8.4%를 곱하면 약 813명입니다.

- 비율표는 84일(07-13~10-04), 노선 197개의 시간대 자료로 만들었습니다. 표본이 적은 노선은 전체 평균 비율을 약하게 섞었습니다(섞지 않으면 13.8%, 섞으면 13.9%로 차이가 없었습니다).
- 하루 합계에는 실제 값을 써서 비율만의 오차를 쟀더니 전체 13.9%였습니다. 노선 구분 없는 전체 평균 비율은 22.3%라서 노선별 비율이 필요합니다.
- 마지막 1주를 빼 두고 한 번만 본 시험에서 비율만 13.6%, 일별 예측 오차까지 합친 값은 평일 16.2%, 전체 17.4%였습니다.

## 8. 측정 조건과 범위

- 이용량 자료가 합성데이터이므로 오차는 정답값 기준입니다.
- 시간대 자료는 7~10월이라 겨울 시간대 비율은 측정 범위 밖입니다.
- 휴가 구간은 여름 자료를 보고 정했고, 여름은 두 번입니다.
- 명절은 표본이 3일이라 시간대 오차가 27.0%로 큽니다. 작은 노선도 32.7%입니다.
- 예측 가능 기간은 학습 마지막 날 + 56일까지입니다.
